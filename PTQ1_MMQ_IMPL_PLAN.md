## 0. Goal (one line)
Get PTQ1_0 prefill on ROCm gfx1100 off the dequant+hipBLAS path (697 t/s) onto the native
packed MMQ path. Precedent: PQ2_0 on the same machine does 888 t/s pp with exactly this
path. Target ~850 t/s pp. Decode (36 t/s, native mmvq) is independent of MMQ and stays.

### 1.2 The codec (WIP, verified against CPU refs)
- PTQ1_0: group-128 ternary (values -d/0/+d), base-3 trit packing: 5 trits/byte in
  qs[24] = 120 values (16-byte + 8-byte chunks), 4 trits/byte in qh[2] = 8 values,
  one fp16 d per 128. Same packing as upstream TQ1_0, group 128 instead of 256.
- Dequant: recurrence t = (v*3)>>8 with v = (v*3)&0xFF, out = (t - 1) * d.
- CPU refs: quantize_row_ptq1_0_ref (ggml-quants.c:148), dequantize_row_ptq1_0 (:564).

### 1.3 Why PTQ1_0 is slow on HIP today
- All 9 MMQ sites are #if !defined(GGML_USE_HIP) -> should_use_mmq() falls to
  default: false for PTQ1_0 on HIP -> ggml-cuda.cu takes dequantize (5.95GB packed ->
  ~54GB fp16) + hipBLAS = 697 t/s pp.
- Decode is already native: mmvq.cu vec_dot_ptq1_0_q8_1 (unguarded) = 36 t/s,
  unpack-ALU bound, independent of MMQ. No change expected there.

### 1.4 Intrinsics: NO new code needed (the "hard part" dissolves)
- load_tiles_ptq1_0 + decode_ptq1_0_qs4 (mmq-load-tiles.cuh:263-359, guarded) use
  __byte_perm (4 calls) and __vsub4 (2 calls, both "subtract 1 from a trit byte").
- Both already work on HIP, proven by code that runs today:
  - __vsub4 shim: vendors/hip.h:275 -> __vsubss4 (saturating). Exact for trits:
    inputs are only {0,1,2}, so 0-1, 1-1, 2-1 all fit int8 and saturation never
    triggers. Already exercised by the PTQ1_0 dequant kernel (convert.cu:153) and
    the mmvq kernel (vecdotq.cuh:939).
  - __byte_perm: resolves under HIP (ROCm side) - the identical calls in vecdotq.cuh
    (decode, runs at 36 t/s) and convert.cu (dequant, runs in the 697 t/s path)
    compile and run on HIP today.
- => The port is guard removal + config wiring. No emulation work.

## Gotchas / risks
- The __vsub4 shim is the SATURATING variant (vendors/hip.h:275 -> __vsubss4). It is exact
  here only because trit bytes are {0,1,2}. Do NOT reuse this pattern for general byte data.
- Phase 0 is a precondition for everything: until rdna3.cuh exists, the tree does not
  compile at all (PQ2_0 included).
- Never touch the CUDA max_batch/turing semantics (sites 2/3) - they are the A/B knobs
  for CUDA deployments (env GGML_CUDA_PTQ1_0_MMQ_MAX_BATCH).
- The PTQ1_0 dp4a util entry reuses the generic vec_dot_q8_0_q8_1_dp4a / write_back_dp4a
  (same as PQ2_0): the x tile holds int8 trits {-1,0,1}, no PTQ-specific vec_dot needed.
- Do not commit anything; the WIP stays uncommitted until the user decides.
- GPU0 must stay free: always HIP_VISIBLE_DEVICES=1.

Findings:
- No measurable win on gfx1100: MMQ 741.3 vs pre-port 744.5 (pp512, within noise);
  pp5201 703.7 vs 686-697 (+1-2%). The ~850 t/s target is not met.
- The PQ2-vs-PTQ1 gap is path-independent: ratio 0.79 pre-port (697/886), 0.80
  post-port (741/921). Both GEMM paths (dequant+hipBLAS and packed MMQ dp4a) pay the
  same base-3 trit decode cost (5-iteration recurrence per 5 trits, ~4 ALU ops/value
  vs 1-2 for PQ2_0's 2-bit unpack) and hit the same RDNA3 ALU ceiling.
- Output sanity OK (coherent thinking-mode text, factually correct; the earlier
  "We need..." probe output was the thinking prefix, not degeneration). PQ2_0 no
  regression (921.5/47.4 vs 926.9/47.5). tg128 unchanged (36.1 vs 36.3, mmvq path,
  as designed).

Decision: KEEP the port. It is the clean native path (removes the dequant+hipBLAS
fallback, CUDA/HIP parity, zero speed downside) and the foundation for any future
decode work. WIP stays uncommitted. Closing the PQ2 gap requires a lighter PTQ1_0
decode (repack/requant), a separate project, not MMQ.
